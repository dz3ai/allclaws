你给 agent 配了七八个 MCP server：文件系统、浏览器、数据库、GitHub……配置写了一份又一份。然后某天，agent 突然「变笨了」——某个 server 悄悄挂了，工具列表少了一半，agent 一个字不提，只是开始频繁地说「这个我做不到」。你翻半天日志才发现：是它背后的那个本地应用根本没启动。

再或者：你在新机器上导入配置，一堆 server 集体报错。为什么？因为配置文件只记了「怎么启动进程」，没记「这东西依赖什么才能活」。命令能复制，依赖复制不了。

最后是钱的问题。每一次对话，agent 的上下文里都驮着所有已挂载工具的完整 schema——不管这轮对话用不用得上。这些不是抽象的抱怨，是我们 7 月做 MCP 深度测量时用 tiktoken 一个个数出来的。

这个场景的共同病根，是我们追踪的 35 个平台之一 **Hermes-Agent** 这周用一次架构级重构正面回答的问题：**MCP server 一直被当成「进程」来管，而进程是个错误的抽象。**

*本文是「MCP 产品化观察」系列第 1 篇。下一篇看 Codex 那条「多租户协议」路线的细节。*

---

## 病根：进程抽象的三个盲区

把 MCP server 当进程管，具体错在哪？拆开看是三个没人负责的盲区。

**存在性盲区**：配置文件说「启动这个命令」，但它不回答「这台机器上装没装它依赖的那个应用」。没装，你就得到一个启动失败的进程和一行看不出原因的错误。配置在机器之间不可移植——因为「依赖声明」这个概念在配置格式里根本不存在。

**存活性盲区**：server 起来之后，它的生命周期就和 agent 各过各的了。背后的应用退出了？server 变成僵尸，工具目录还挂在 agent 的上下文里，占着 token、喊着不存在的能力。agent 对「工具为什么突然没了」毫无感知，只会表现出「变笨」。

**依赖性盲区**：一个 MCP server 往往就是某个应用的「接线柱」——浏览器类的 server 依赖浏览器，代码类的依赖 IDE。但这个关系在今天的集成层里是隐形的，没人声明、没人检查、没人跟随。

三个盲区叠在一起，日常体验就是开头痛感的来源：你实际在充当一整套手工的依赖管理器——凭记忆知道哪个 server 靠哪个应用活着，凭肉眼发现哪个挂了，凭经验猜为什么挂。人在做机器该做的事，而且是这台机器上唯一不知疲倦的组件在做最琐碎的事。

三个盲区指向同一个结论：**MCP 集成缺的不是更多 server，是一层依赖管理。**

## 先算笔账：僵尸工具不只是碍事，它按 token 计费

聊架构之前，先把「进程抽象的代价」量化。AllClaws 7 月的 MCP deep-dive Phase 3 报告（static reconstruction 方法：用 10 个官方 MCP server 构造代表性 payload，逐平台复刻其上下文处理逻辑，用 tiktoken cl100k_base 计数）给出过一组硬数字。

eager 全量挂载的基线：**N=1 server 是 8 个工具 560 token，平均每工具 70 token；N=3 是 26 个工具 2,034 token；N=5 是 37 个工具 2,821；N=10 是 56 个工具 3,998**。平均下来，**每个 MCP 工具的全量 schema 约 73 token**。这 3,998 token 不会因为你这轮对话只用一个工具而打折——eager 模式下，它们每一轮都在场。这就是「僵尸工具」的真实账单：不只挡路，还按对话轮数乘以单价持续计费。

好消息是行业并没有躺平。同一份测量里，**ZeroClaw** 的 deferred loading（轻量 stub + `tool_search` 工具）在 N=10 时把开销压到 1,107 token，**省 72.3%**；**GoClaw** 的 search mode 更激进——agent 只看到一个搜索工具，不管你配了多少 server，开销恒定 **183 token**，**省 95.4%**。还有个中间态：**Reasönix** 的 canonicalized schema 把 N=10 从 3,998 压到 3,859，只省 3.5%——但它真正省的是间接成本，规范化后的 schema 提高缓存命中率，这部分要靠真实 API 调用才能测出来。

瘦身也不是免费的。**ZeroClaw deferred**（stub + 搜索）：LLM 每次用 MCP 工具前必须先调一次 `tool_search`，多一轮往返。按报告的测算，10 轮对话里用 3 个 MCP 工具，就多 3 次搜索调用，每次约 150 token——但对比每轮都驮着 56 个完整 schema（3,998 token），依然是压倒性划算；stub 本身也随工具数线性增长，只是斜率从每工具约 73 token 降到约 15 token。**GoClaw search**（恒定 183）最彻底，但代价是 agent 失去了「我有哪些工具」的全局视野，每次都要靠搜索发现工具——工具选择从「看菜单点菜」变成「报菜名问厨房有没有」，对模型的规划能力要求更高。

这组取舍说明 token 优化没有银弹：省的是上下文，付的是往返或规划复杂度。但方向已经明确——eager 全量挂载正在退场。

这组数字和这周的 Connectors 重构是同一枚硬币的两面：token 优化解决「工具目录多大」，Connectors 解决「工具目录里什么是真的」。一个管体积，一个管真伪——两个问题不解决，MCP 集成都谈不上工程化。

## Hermes 的答案：Connectors 三部曲

这周 Hermes-Agent 的发布（近 7 天 4,844 commits，v2026.9.21 于 09-21 发布，周级发版节奏）里，主线不是修修补补，而是一组编号连贯的架构动作——NS-941/942/943 三部曲，产品名叫 **Connectors**。三个动作正好对着上面三个盲区各打一枪。

**第一枪，换掉认知框架。** Desktop 端的 Connectors 页面正式取代了原来的 MCP tab。别小看改个名字：用户面对的概念从「我要管理一堆 server 进程」变成了「管理一组连接器」——管理的对象从进程变成了集成关系。这是整个重构的定调动作。

**第二枪，NS-942：Portable plugins 声明依赖。** 插件的 manifest 里现在要写清楚「我这个 server 依赖哪个应用」。关键在后半句：**安装的时候，在不支持的主机上直接拒绝**。注意这个方向——不是装完之后跑不起来再报错，是装都不给你装。配置第一次有了「可移植性契约」：能装，就代表依赖满足；依赖不满足，你在第一步就知道，而不是在第三步的日志里猜。存在性盲区，这么堵上的。

**第三枪，NS-943：Application-backed MCP servers，生命周期跟随应用。** server 的 live endpoint 每次尝试连接时即探测；工具目录随应用的存活状态动态伸缩——应用活着，工具在；应用死了，工具从目录里退场，而不是留一具僵尸占着上下文；错误信息会说明原因，告诉你「为什么连不上」，而不是一句干巴巴的 timeout。存活性盲区和依赖性盲区，一并处理。

把三部曲连起来读，你会发现它在说一件事：**MCP server 从「进程配置」被提升为「应用依赖对象」。** 装不装，看依赖声明；活不活，看应用状态；为什么挂，有明确解释。这是把软件工程里最成熟的那套依赖管理思想——package.json 管依赖、容器镜像管环境——搬进了 agent 的工具层。

这套思想的历史战绩值得信任。npm 之前，前端工程师手工下载脚本放进 lib 目录；Docker 之前，运维写「部署文档」祈祷新机器能复现旧环境。每一次「隐式依赖 → 显式声明」的迁移，都让「在我机器上是好的」这句话离死更近一步。MCP 现在正站在同样的关口，而 agent 场景甚至更迫切——因为 agent 的工具目录不是静态的，它跟着背后应用的生死动态变化，没有声明和探测，连「当前应该有什么」都无法回答。

## 幕后基建：resolver 的三层探测

声明了依赖，还得有人去验证依赖。这周同步落地的还有配套的 `hermes_platform.resolver`，三层结构：locate（找到应用在哪）、inspect（看清它是什么版本、什么状态）、probe（探测它的 endpoint 通不通），外加 AppResolver 抽象和 gh lookup。

为什么说「探测」是依赖管理的核心动词？因为前面所有设计——安装拒绝、工具目录伸缩、错误说明原因——每一个决策的原料都来自探测结果。没有 resolver，manifest 里的依赖声明只是一行注释；有了持续探测，声明才变成活的约束。

这也解释了为什么这组改动要连着 kanban 的一组修复一起落地（连接切换时查询键跟随 activeConnectionId 反应式重建）：一旦「连接」成为系统里的一等对象，所有围着连接转的状态——看板、查询、订阅——都得跟着它走。这不是一个功能的落地，是一个新概念入场所需要的配套迁移。

## 同一周，另一条路线：Codex 把 MCP 当协议治理

有意思的是，同周的 **Codex**（OpenAI）走了另一条路。两条路线放在一起看，能看清 MCP 产品化的全貌——按同一组问题对齐着看。

**Hermes：应用依赖路线。** 核心比喻：MCP server 是应用的依赖项，像 package.json 管依赖。关键机制：manifest 声明依赖 + 安装时拒绝 + endpoint 持续探测 + 工具目录伸缩。解决什么：单机用户的「server 装不上、悄悄死、说不出原因」。这周动作：NS-941/942/943 三部曲 + resolver 落地，v2026.9.21 发布。

**Codex：多租户协议路线。** 核心比喻：MCP 是多租户协议，请求要有身份和上下文。关键机制：MCP resource reads 带 app/account targets + trace context 跨 transport workers 保留。解决什么：一个 agent 服务多个应用、多个账号时的请求归属与可追溯。这周动作：app-server v2 持续演进，rust-v0.155.1 于 09-18 发布。

两条路线的分歧点是「MCP 集成的第一性问题是什么」。Hermes 认为是单机依赖：用户的痛在「装不上、悄悄死」。Codex 认为是身份：当 agent 背后站着多个 app 和账号，每个 MCP 请求属于谁、trace 谁查得到，才是根本问题。两条路线不互斥——前者管本地可靠性，后者管服务端正确性，合在一起才是完整的图。

还有第三个小注脚：**kimi-code** 这周的 MCP OAuth 请求加上了 offline_access（#3979）——MCP 的授权也要考虑「令牌过期了，server 还能干活吗」这种 OAuth 生命周期问题。加上上周 kimi-code 的 per-server MCP deferred disclosure（每个 server 的工具延迟披露，减少首屏 token 开销），token 瘦身这条线也还在延伸。

三条线索拼起来是一个清晰的判断：**MCP 集成正在从「进程启动时挂载」演进为有依赖契约、有身份、有 OAuth 生命周期的完整集成体系。** Hermes 管依赖契约，Codex 管身份与追溯，kimi-code 管授权生命周期——三家人从三个不同入口，爬向同一层。

## 放回这周的生态坐标

以上不是孤立事件。按我们 9 月 22 日的 submodule 周报（覆盖 29 个仓库路径、35 个平台），这一周 13 个平台有 commit、11 个发布新版本——openclaw v2026.9.5、reasonix desktop-v1.38.11、hiclaw v1.2.4、nanobot v0.3.5、praisonai 周内三连发 4.7.8/9/10，还有 Moonshot 把 kimi-cli 正式归档、kimi-code 跳版发布 2.0（0.43.x 直跳 2.0，架构换到 agent-core-v2）。

热闹之中，MCP 产品化是少数「多家平台同周推进、且方向可叠加」的主线。当模型路由（另一个同周范式信号，**HiClaw** 和 **AgentScope** 同周把「哪个 agent 用哪个模型」做成显式路由层）解决「谁干活」，MCP 的这层重构解决的是更基础的问题：「agent 的手」——工具层——什么时候可用、为什么不可用、换台机器还可用不可用。地基的工程，不抢眼，但决定上面能盖几层楼。

值得一提的是，kimi-code 2.0 的 agent-core-v2（DI × Scope 四层引擎）虽然是会话管理侧的大动作，但它跟工具层是配套的：transcript 做了 L1 粒度存储到 L4 框架无关视图的四层数据层，工具调用的记录、回放、审计都有了结构化的地基。工具目录「伸缩」这种动态行为，恰恰需要这种数据层支撑——目录变了谁记得变过、怎么变回去，都是存储问题。会话架构和工具架构在同时升级，这不是巧合，是多 agent 系统整体在从「能用」迈向「可运营」。

顺带一提，连治理面也在同周呼应：RocketRide 发布了 client-mcp-v1.5.0-prerelease（09-14），OpenClaw 的根 AGENTS.md 出现了「Codex sibling runtime hard gate」——任何涉及 Codex 协议的改动必须亲自检查 `../codex` 源码才能下结论。工具生态的相互依赖，已经强到要写进 agent 协作规范了。

## 为什么是现在：成本压力正在传导到架构层

回头看，这波 MCP 重构不是凭空发生的。同一份周报里有条跨项目洞察很说明问题：**prompt/token 瘦身运动正在头部平台间扩散**——OpenHuman 合并了 hermes-prompt-diet PR，多个 agents/tools 的 prompt 预算上限集体下调；Eliza 把 batch-scope 规则改成只在提示里声明一次；ZeroClaw 把历史裁剪从「裁到上限」改成「裁到低水位目标」；kimi-code 专门做了 CLI 启动时间与内存削减。

四家平台，互不相干，同一个月里都在做同一件事：砍上下文和启动开销。这是 token 成本压力传导到架构层的直接证据。而 MCP 工具目录恰恰是上下文里最「死重」的部分——按我们前面的测量，10 个 server 就是近 4,000 token 的常驻负担，且随着你接入的生态越多越重。

再往深一层看，还有个结构性推手：agent 的能力半径在扩张。这周 ZeroClaw 把 WhatsApp 做成一等公民（原生投票、inline 图片预览、方言化 Markdown 渲染），nanobot 补全了 Copilot device sign-in 的完整浏览器流程，Reasonix 一周两版都在磨桌面端深水区。agent 触达的外部系统越多，挂在它身上的 MCP server 就越多，工具目录的膨胀是能力扩张的必然副产物。不解决依赖管理和目录伸缩，「接更多生态」和「上下文爆炸」就是同一枚硬币——你要哪一个，就得两个都要。

所以 Connectors 出现的时机就很好理解了：当所有平台都在给上下文「减脂」，MCP 这块最大的脂肪自然首当其冲。减体积（deferred/search 模式）和保真伪（依赖契约、存活探测）必须同时做——只做前者，省下的 token 被僵尸工具的 stub 继续占着；只做后者，真实的工具目录依然庞大。Hermes 这周选的是后者，配上上周 kimi-code 的 deferred disclosure，两条腿都有人在走。

## 给你的 MCP 配置做三个检查

不用等 Hermes 的方案普及，今天就可以用这三个问题审一遍自己的 MCP 集成。

**你的配置是「进程清单」还是「依赖清单」？** 如果配置里只有 command/args/env，没有任何一行回答「这依赖哪个应用、什么版本」，你的配置就是不可移植的——换机器必然翻车，只是早晚问题。给每个 server 手写一行依赖注释，都比没有强。

**server 死了，你的 agent 知道吗？** 工具目录是启动时一次性挂载，还是跟随存活状态更新？如果 agent 会拿着僵尸工具的 schema 继续对话，那它不仅做不了这件事，还在按我们前面算的账单持续付 token——每个僵尸工具约 73 token，每轮都在场。健康检查 + 目录同步，是最值得先补的两块。顺带考虑目录体积：如果配了 5 个以上 server，deferred 或 search 模式应该进你的选型清单，72%~95% 的上下文节省不是小数。

**失败时，错误信息说「原因」了吗？** 「连接失败」和「目标应用未运行，请先启动」是两种完全不同的运维体验。把 resolver 式的 locate/inspect/probe 分层探测思路借过来，你的报错就能从「现象」升级到「原因」。更进一步，把探测做成常态化的——不是出事了才查，而是每次连接尝试都探测，让目录伸缩跟着探测结果走，这才是 Hermes 这套设计的完整闭环。

三个检查做完，你会对自己的 MCP 集成有个新认识：你管理的是一堆进程，还是一组有契约的依赖。这个认识的差距，就是这周 Hermes 用一部架构重构展示的差距。

MCP 的故事接下来怎么走？按这周的三条线索外推：依赖契约会标准化成 manifest 的通用字段，身份与追溯会跟着 app/account targets 进协议层，token 体积问题会催生更多 deferred/search 模式成为默认。当这三件事各自成熟，MCP 才真正从「协议」长成「集成体系」——到那时，没人会再想起我们曾经用过「进程配置」这种原始办法。
